# Прямое подключение к WebSDR

Клиент приложения работает без WebView и без выполнения JavaScript сервера.
Наблюдения проверены на University of Twente и WebSDR Maasbree.

## Последовательность подключения

1. HTTP GET `tmp/bandinfo.js` относительно адреса приёмника. Читаются только
   дескрипторы `bandinfo`: `centerfreq`, `samplerate`, `vfo`, `maxzoom`, `maxlinbw`, `name`.
   Частоты и частота дискретизации в этом файле указаны в кГц.
2. WebSocket `/~~stream` для демодулированного звука.
3. Отдельный WebSocket `/~~waterstream{band}?format=9&width=1024&zoom={zoom}&start={start}`.
4. LIVE устанавливается после начала воспроизведения PCM в AudioTrack.
   Водопад имеет отдельное состояние и может восстанавливаться без остановки звука.

Для HTTP используются `ws`, для HTTPS — `wss`; транспорт обеспечивает OkHttp.
Origin и адреса потоков соответствуют конечному адресу после перенаправлений HTTP.
STOP и потеря audio focus завершают соединения и отменяют повторные подключения.
Ошибки звука и водопада восстанавливаются независимо с задержкой 1–30 секунд.
Результаты старых соединений отсеиваются по поколениям сессии и отдельных потоков.
Общий тайм-аут загрузки описания сервера — 20 секунд.

## Команды

Команды — текстовые WebSocket-сообщения, а не отдельные HTTP-запросы:

```text
GET /~~param?f=7100.000&band=0&lo=-2.7&hi=-0.3&mode=0&name=Radiola
GET /~~waterparam?band=0&zoom=1&start=8192&slow=2&scale=1
```

`f`, `lo`, `hi` задаются в кГц. Режим 0 — линейный детектор для SSB/CW,
1 — AM, 2 — синхронный AM, 4 — FM. USB/LSB выбираются знаком полосы.
В CW частота BFO учитывает сдвиг звукового тона относительно отображаемой частоты.
WFM в клиенте не предлагается. Доступные диапазоны берутся у конкретного сервера.

Команды настройки отправляются без дополнительной задержки (объединяются только
вызовы внутри одного прохода UI), команды окна водопада — с интервалом до 100 мс.
Непрерывный ввод не откладывает их отправку до остановки; последнее значение
доставляется отдельно. `zoom/start` меняются в существующих соединениях. Сервер
должен подтвердить координаты; при отсутствии данных клиент восстанавливает только
водопад. Переключение диапазона создаёт новые потоки водопада.
На медленном сервере следующее окно ждёт первой подтверждённой строки предыдущего;
промежуточные положения заменяются последним. Это предотвращает голодание водопада
при непрерывном движении. Настройка звука от подтверждений водопада не зависит.

BW использует отдельные профили WebSDR. Ограничения линейного детектора берутся из
`maxlinbw` (предельные края фильтра, как у клиента сервера), FM — до ±15 кГц.
Default в меню совпадает с применяемой полосой. Выбор полосы сохраняется по модуляциям.

## Бинарный звук

Одно сообщение содержит несколько записей, а не один PCM-блок:

| Метка | Содержимое |
| --- | --- |
| `F0–FF` | S-meter, два байта |
| `80` | 128 отсчётов G.711 A-law; сброс предиктора |
| `81` | Частота дискретизации, uint16 big-endian; не фиксированные 48 кГц |
| `82` | Масштаб квантования, uint16 big-endian |
| `83` | Флаги декодера и фильтра |
| `84` | 128 нулевых отсчётов; сброс предиктора |
| `85`, `87` | Дополнительные частотные/временные данные |
| `86` | Маркер синхронизации |
| `90–DF` и старший бит 0 | 128 отсчётов адаптивного сжатия |

Сжатые блоки используют кодирование остатков переменной длины и адаптивный
20-компонентный предиктор. Состояние предиктора, интегратора, масштаба и флагов
сохраняется между WebSocket-сообщениями. Декодер воспроизводит знаковые 32-битные
операции и оборачивание PCM16. Считать эти данные готовым PCM или декодировать
только A-law нельзя.

AudioTrack принимает моно PCM16 с переданной сервером частотой. Его владелец —
отдельный поток; очередь ограничена 200 мс при любой частоте дискретизации. При
переполнении удаляется старый PCM; сетевые пакеты декодируются полностью и по порядку.
Начальное заполнение — 40 мс. После underrun воспроизведение получает доступный
PCM сразу, без искусственной паузы для повторного накопления буфера.
При перестройке частоты и модуляции PCM не
очищается. Системный аудиотракт выполняет ресэмплинг. Ошибки и остановка записи
AudioTrack ограничены тайм-аутом и восстанавливаются в аудиопотоке.

## Бинарный водопад

Форматы 9 и 10 используют контекстное кодирование разностей между строками;
10 дополнительно уточняет малые изменения каждого бина. Клиент запрашивает 9,
поддерживаемый также проверенными старыми серверами.

- `FF 01`: подтверждение zoom/start; start — little-endian в байтах 3–6.
- `FF 02`: изменение ширины и сброс уровней.
- `FF FF`: экранирование первого байта строки.
- Остальное — сжатая строка. Состояние предыдущей строки обязательно сохраняется.

Размер окна: `band.spanHz / 2^zoom`. Единица start соответствует
`band.spanHz / (1024 * 2^maxzoom)` Гц. До подтверждения координат окно не публикуется.
При смене диапазона закрывается предыдущий поток водопада и очищается история.
Полученные уровни отображаются как относительная интенсивность REL 0–100, не как
измеренный dBFS. Показания S-метра берутся отдельно из звукового потока.

Объединение частей строки выполняется вне UI. В главный поток поступает последнее
готовое изображение с ограничением до 30 обновлений/с; промежуточные декодированные
кадры могут заменяться. FPS в карточке измеряется, а не задаётся константой.

## Жизненный цикл и диагностика

Владелец сессии — `WebSdrRuntime` в Application, воспроизведение поддерживает
`WebSdrService`. Уничтожение Activity не отключает сервер. Сохраняются источник,
сервер, частота, модуляция и полоса; после уничтожения процесса подключение
запускается пользователем. В онлайне не прогревается неиспользуемый USB AudioTrack.
Карта кеширует геометрию и каталог между посещениями, поддерживает список серверов.

Лог `WebSdrMetrics` содержит измеренный FPS, накопленный PCM в миллисекундах,
удалённый PCM, underrun, восстановления AudioTrack и аудиомаршрут. Это локальные
показатели, а не измерение полной задержки от сервера до динамика.

## Проверки и границы

`WebSdrProtocolTest` сравнивает PCM и строки обоих форматов с эталонными результатами
для записанных сетевых пакетов. Дополнительно проверяются усечённые данные, A-law,
тишина и разбор диапазонов без выполнения JavaScript. Файлы эталонного клиента
сервера в приложение не включены.

`WebSdrControlTest` проверяет доставку последней команды при непрерывном вводе,
временную границу аудиоочереди при разных частотах дискретизации и профили BW.
`WebSdrWaterfallStreamTest` проверяет смену координат через те же WebSocket-соединения.
`WebSdrLifecycleTest` запускается на Android с локальным сервером: стабильный приём,
изменение окна, уход в фон, пересоздание Activity, отдельные обрывы звука/водопада,
восстановление и STOP во время ожидания повторного подключения.

На телефоне проверены подключение, оба потока, смена режима/диапазона, настройка,
масштабирование, переход MAP/Radio и DISCONNECT. Серверы с авторизацией, нестандартным
описанием диапазонов или другим протоколом могут потребовать отдельной поддержки.

### Native viewport resolution

The online client assembles two adjacent 1024-bin streams into a 2048-bin RF row
when server zoom is available. Each stream retains a separate stateful decoder;
rows are published after both tiles update. The combined span is
`band.spanHz * combinedWidth / 1024 / 2^zoom`, and each tile start advances by
`1024 << (maxzoom - zoom)`. A server may accept a wider width parameter while
still returning 1024 bins, so stream width remains 1024.

The online bitmap retains the complete combined row. When finer RF data arrives,
existing history remains positioned by each row's own RF coordinates and span. The USB rendering
resolution policy and its 8192-bin input history remain unchanged.
